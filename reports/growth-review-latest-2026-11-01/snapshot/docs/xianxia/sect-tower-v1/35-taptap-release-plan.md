# TapTap 首发架构与引擎调整方案

日期：2026-10-28  
阶段：功能 Alpha → Android 原生可发布版本的技术规划  
状态：**本文件是建议方案，尚未实施 Android 改造、接入 TapSDK、生成签名包或提交商店。**

## 1. 建议结论与适用范围

继续使用 **Cocos Creator 3.8.8、TypeScript 表现层、现有纯 JavaScript 规则层**，新增 Android 原生构建与平台适配。先固定当前引擎版本完成可运行验证；只有发现具体 SDK、工具链或设备兼容问题，才评估同一 3.8 系列的升级，不把换 Unity/Godot 或重写引擎作为上线前置。

本方案暂按 **TapTap 中国大陆、Android 优先、横屏 2D、剑修＋九层塔、现有免费资源抽取**规划。未将广告、充值、交易、排行榜、多人玩法加入首期。地区、终端或商业模式改变时，需要重新核对相应渠道政策与服务边界。

Cocos 官方文档已有 Android 原生工程生成、编译及 JS/Java 通信路径。TapSDK 当前官方文档提供 Android 原生接入；采用 Cocos 到 Android 的薄适配即可，不要求重写玩法或把游戏做成实时联网服务。[S1][S2][S3]

`game-engine` 是开发指导 skill，不是游戏运行依赖；其安装不会改变项目引擎和构建产物。

## 2. 本地代码审查结果

| 当前事实 | 对 Android 上线的影响 | 最小调整 |
|---|---|---|
| `cocos-pilot/package.json` 指定 Creator 3.8.8 | 已有可继续使用的引擎项目 | 保留场景、脚本和 UUID |
| `js/xianxia/TowerRun.js`、`TowerCampaign.js`、`TowerGrowth.js` 独立于 Cocos 表现 | 战斗、成长、事务、测试可以继续复用 | 继续由 `scripts/cocos/sync-shared.mjs` 生成 shared，禁止分别维护两套规则 |
| `PinePilot.ts:25` 用 `sys.isBrowser && query.tower` 选择塔模式 | 原生启动会走旧 SurvivorView | 构建配置默认明确为宗门塔，浏览器参数只用于开发预览 |
| `TowerView.ts:45/61/322` 通过 `typeof window` 后读取 URL、DOM 或 history | 原生可能存在 window 全局，但不具备浏览器 API | 对浏览器功能使用平台能力判断，将启动参数传入宿主 |
| `scripts/cocos/build.mjs:7` 只接受 web-mobile / wechatgame | 当前没有 Android 产物流水线 | 新增 Android 配置及原生工程编译步骤 |
| `scripts/check-release.mjs` 绑定微信 AppID、分包路径 | 现有 release 命令不能证明 TapTap 包合格 | 拆为共用检查＋平台专属检查 |
| `SurvivorPlatform.ts` 已统一生命周期及 `sys.localStorage`，但安全区和震动主要面向 wx | 可扩展已有适配，不必另造一套宿主 | 补 Android 安全区、返回键、震动和平台服务 |
| Campaign 已有 schema、checksum、写入后发布状态及并发变更检查 | 具备本地可靠性基础，但不是原生持久性或防作弊证明 | 增加有效备份、原生强杀/覆盖安装验证、账号隔离 |
| `TowerView` 无条件提供体验工具入口 | 关闭 Cocos debug 不会自动关闭业务无敌工具 | 正式构建同时关闭入口、执行路径、测试注入和调试暴露 |
| 塔表现仍主要为 Graphics，旧模式资源加载在 SurvivorView | 不能认为塔模式已经接入全部角色图集和音效 | 先验证实际使用资源，再分批替换美术与声音 |

以上为源码审查证据，**没有据此宣称 APK 已能运行**。此前 Web 测试和浏览器截图只能证明对应 Web 构建。

## 3. 目标架构

```text
Cocos 表现层
宗门 / 技能树 / 塔内场景 / 输入 / 动画 / 音效
                    │ 发出玩法命令、读取状态
                    ▼
现有游戏规则层
TowerCampaign ─ 永久成长、物品事务、存档版本
TowerRun      ─ 固定步战斗、掉落、波次、暂停快照
Growth/Content/Loot ─ 技能、境界、内容与数值版本
                    │
                    ▼
平台接口（从现有 SurvivorPlatform 扩展）
启动配置 / 生命周期 / 安全区 / 存储 / 账号 / 云存档
           ┌────────┴────────┐
           ▼                 ▼
Web 开发预览            Android 原生宿主
浏览器适配             Cocos JS ↔ Java/Kotlin 桥
                              │
                     按需接入 TapSDK
                 登录 / 实名防沉迷 / 云存档
```

接口只抽取本轮确有平台差异的能力，不引入通用服务框架、全局事件总线或 ECS 重写。

建议职责：

- `LaunchConfig`：默认模式、环境、是否允许测试工具；发布包不依赖 URL。
- `PlatformAdapter`：生命周期、返回操作、安全区、触感与系统信息。
- `SaveRepository`：本地读写、备份、迁移、账号命名空间；保持 Campaign 事务仍为游戏状态入口。
- `AccountService / CloudSaveService`：封装 SDK 异步回调、取消、超时、离线及账号切换。
- `BuildProfile`：Web 开发、Android 内测、Android 发布三种配置，明确各自功能和存档边界。

Android SDK 回调必须回到游戏线程处理，通过结构化数据传参，避免拼接可执行字符串。登录、云下载、支付等外部事件不得直接修改 UI 所持状态；由领域层验证后提交。[S2]

## 4. 首期服务与存档策略

### 4.1 本地运行战斗，平台服务按需联网

塔内战斗、角色移动、技能释放继续在本地执行，避免每次攻击请求服务器。网络用于账号、适用的实名认证/防沉迷检查、云存档、版本信息及必要诊断。

“本地战斗”并不承诺大陆发行包可以无条件离线进入游戏。实名、防沉迷及离线准入必须按最终适用的政策和 SDK 结果实现；网络失败不能自动当作验证通过。[S5]

### 4.2 云存档在公开测试前完成

建议首个技术 APK 先验证本地存档；公开测试前增加 TapTap 登录和云存档。TapTap 官方云存档依赖 TapTap 登录，不等于安装 SDK 就自动备份，也不替开发者解决游戏内数据冲突。[S4]

具体规则：

1. 本地写成功才发布新状态，失败维持现有冻结/重试流程；保留最近有效备份。
2. 云端同步采用账号 ID、存档 schema、revision、设备标识及内容版本；账号切换先暂停并持久化，禁止串档。
3. 云存档只在进入宗门、完成一层、重要养成事务和安全暂停点合并上传；不把每个战斗 tick 或当前每 0.75 秒本地 checkpoint 都上传。
4. 单存档串行上传，失败进入重试队列；保留云端返回的版本和冲突信息。
5. 双设备冲突不把资源数量、装备或技能简单相加。展示两份进度摘要并备份冲突副本，再由玩家选择继续哪份。
6. 云恢复后先执行原有完整验证与迁移；新面额/掉落版本不能在读取旧挑战时被静默重解释。
7. 场外缓慢回血继续遵守用户确认的规则。补充时钟回拨、长时间离线及时间同步异常测试；如未来引入有商业价值的时间收益，必须以可信服务时间和服务端结算为准。

checksum 用于检测损坏，不能证明玩家没有改档。当前免费单人玩法可接受这一信任边界；若以后增加付费资源、交易、竞争排行榜，再将钱包、抽取、兑换和付费权益迁到服务端权威事务，不把任意客户端云存档当作可信经济账本。

### 4.3 暂不自建完整游戏服务器

本阶段优先复用平台登录与云存档，避免同时维护战斗服务器、微服务和数据库。若 SDK 接入要求 token 验证或后续功能需要服务端，仅增加对应的小型服务。

未来确需服务端时，保留 JS 规则层的复用价值，但共享规则代码不等于信任客户端结果。服务端仍需独立验证授权、消耗、奖励、随机结果与幂等事务。

## 5. Android 包必须补齐的工作

### 构建与签名

- 固定包名、版本名、递增 versionCode；包名由发行身份决定，不能临时使用示例包名。
- 新增 Android 构建配置，生成原生工程并通过 Gradle 编译。引擎、JDK、SDK、NDK、Gradle、AGP、TapSDK 版本形成经验证的锁定清单；不直接采用文档中的 `latest` 示例作为生产依赖。
- 至少完成 ARM64 原生库构建与真实安装。TapTap 的官方包规范要求支持 ARM64；各 SDK 的 `.so` 也必须纳入检查。[S6]
- 使用独立保管的正式签名，验证同签名覆盖升级；签名私钥不写入仓库或日志。
- 内测包与发布包在构建配置、工具可用性、服务环境、存档策略上明确区分。签名/包名最终确定前，不生成或分发声称可长期覆盖升级的正式包。
- 新增 Android 专用 release 检查：产物存在、包名/版本/签名、ABI、权限、资源清单、无测试入口、SDK 配置及对应源码版本。

### 设备与生命周期

- 横屏读取真实安全区，统一作用于摇杆、暂停按钮、技能面板和 HUD；验证左右刘海、手势导航、挖孔及平板。
- Android 返回键复用暂停/返回交互；从后台恢复清空触摸状态，不累计后台时间补跑大量战斗帧。
- 测试来电、锁屏、切应用、内存回收、强杀、重新打开、覆盖安装、低存储与写入失败。
- 拒绝权限或隐私同意时显示可理解的结果；按官方要求在用户同意后初始化需要数据收集的 SDK。[S7]
- 实名/防沉迷限制到来时必须暂停并保存允许保留的进度，禁止只关闭提示继续战斗。

### 美术、资源与性能

- 第一张 APK 使用现有可用素材验证闭环；后续美术替换沿用固定角色、武器、图标和怪物资源合同。
- 静态界面、技能图标、角色、怪物、场景和音效分开管理；只加载当前需要的资源。首包先包含可玩内容，后续再依据实际包体决定资源分组。
- 地板、装饰、静态 UI 可预制/缓存；对象池和合批针对真实热点使用。保留必要的动态预警、六边碰撞和战斗逻辑。
- 不为了“原生”把现有战斗全改 C++，也不把换引擎当成解决人物美术与动画质量的办法。
- 本轮建议验收目标：代表设备正常战斗争取 60 FPS，低档设备具备稳定 30 FPS 档；连续 20 分钟高负载测试无崩溃、无持续增长的内存趋势。具体内存、包体、启动时间预算由首个 APK 实测后冻结，不能当成当前已达到的结果。

## 6. TapTap 发行路径

把三个里程碑分开验收：

1. **本地技术 APK**：证明安装、核心游戏与保存恢复；不等于获得公开发行资格。
2. **商店信息/预约与测试筹备**：准备实际玩法录屏、截图、图标、开发者资料和所需资质。
3. **允许的测试或正式下载**：在开发者后台确认对应地区、游戏形态与发行主体要求，资料通过审核后再开放。

TapTap 当前审核规范区分预约/信息展示与开放下载；后者需资质齐全。不能由“免费”“没接充值”推导为不需要审核、备案或其他适用资质。官方材料涉及游戏权属/授权、版号、APP 备案、隐私与实名防沉迷；最终应按本游戏类型、地区和主体向平台确认。[S5][S8]

技术上预留隐私同意、账号、适用的实名防沉迷、设置页资质展示及 SDK 清单。素材验收同时留存字体/音效/图像授权、生成来源和使用记录；商店截图与视频必须对应实机内容，不以概念样片替代已经上线的画面。[S8]

本方案不默认启动付费抽取或广告。若以后增加商业化，应另立需求和服务端权益方案，同时重新核对资格及支付政策。

## 7. 任务拆分与验收顺序

| 阶段 | 负责角色 | 任务 | 验收证据 | 并行条件 |
|---|---|---|---|---|
| A | 主程＋构建工程 | 启动配置、浏览器依赖隔离、Android 配置、原生工程生成 | 不依赖 URL 进入落云宗；可安装技术 APK | 与发行资料准备并行 |
| A | 平台工程 | 原生安全区、返回键、生命周期和存储适配 | 真机后台/恢复/强杀后进度正确 | 接口先约定，可与构建并行 |
| A | QA | 复用逻辑回归，新增原生宿主测试矩阵 | 同一确定性输入的关键规则结果一致；真实交互通过 | 不把模拟结果当设备证据 |
| B | 平台工程 | TapSDK 登录、适用的合规服务、云存档 | 取消/断网/冲突/换号/恢复都可解释且不丢档 | A 的原生包可运行后 |
| B | 数值策划＋玩法工程 | 完成新面额与技能消耗校准，锁定内容/存档版本 | 旧挑战兼容、掉落范围及成长节奏报告 | 可独立于 SDK 开发 |
| B | UI/技术美术 | 宣纸玉青界面收口、塔资源接入、性能热点优化 | 小屏可读、资源无缺失、设备性能录制 | A 性能基线取得后 |
| C | 构建工程＋QA | 发布工具门禁、正式签名、覆盖升级、产物审计 | release 包内测试开关不可执行；升级保档 | 依赖 A/B 合入 |
| C | 发行/产品 | 资质、隐私、实机物料、平台测试/发布配置 | 对应后台审核与分发结果 | 材料可提前，提交需成品证据 |

工作量先以 A 阶段产物校准。未验证原生工具链、设备和 SDK 前，不承诺几天即可正式上架；审核耗时也不包含在编码估算中。

## 8. 第一项应执行的任务

制作 **Android 原生纵向验证包**，验收链路为：

> 安装 → 不带任何 URL 参数进入落云宗 → 学习技能/换剑 → 入塔战斗 → 后台切回 → 强杀重启恢复 → 撤离或通层结算 → 同签名覆盖升级后进度仍在。

这一步先验证当前 Cocos 3.8.8 是否满足实际工程与设备条件，再决定有没有必要升级引擎的小版本。通过后接平台 SDK、公开测试准备及成批美术替换。

本轮只形成上述方案，未变更运行时、正式存档、SDK 初始化或发布开关。

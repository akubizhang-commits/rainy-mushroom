# 栖云宗：保真瘦身与性能优化专项

日期：2026-11-03。状态：立项方案，尚未实施优化。

## 1. 项目结论与范围

目标是在素材清晰度、技能完整表现、战斗规则均不退步的前提下，减少发行资源、缩短等待、降低运行内存和卡顿，支撑 TapTap 发布。

用户已明确：本期不考虑微信；TapTap 安卓安装版或小游戏均可；横屏；不牺牲素材清晰度和技能效果。本方案不把微信包体门槛带入 TapTap，也不把目前 Web 目录体积视为未来 APK 大小。

建议执行路线：**性能基线与平台验证 → 共用低风险优化 → 选择主发布目标并实施对应改造 → 真机验收**。H5 为优先验证候选，不是已经确定的正式发布形式。保留现有 Cocos Creator 3.8.8 与 JS 战斗核心，不重写引擎。

平台选择依据：官方小游戏介绍当前列出普通小游戏与 H5 小游戏。现有项目具备 Web 构建；安卓原生构建尚未接入项目脚本，动态 Canvas 特效需验证。不能认为 H5 构建能直接当作普通小游戏提交，也不能认为把 Web 装入壳中便完成原生适配。具体接入条件、账号可用入口和 SDK 要求在 P0 核验，不在本方案中承诺平台配额或审核结果。

本期不做：微信适配、重新制作素材、改变技能设计、降低怪物数量、减少命中特效、降低显示分辨率、自动降低动画频率、直接上架、购买服务。CDN 如有需要先本地验证，费用和部署另行明确。

### 2.2 已发现的代码事实

- `scripts/cocos/build.mjs` 只允许 `web-mobile` 和 `wechatgame`；安卓流程尚未由该脚本提供。
- `TowerAssetQueue.ts` 会给完成的资源 addRef，直到宿主 dispose 才释放其持有的引用。它实现了复用与重试，但缺少页面/楼层粒度的驻留预算。是否形成实际内存持续增长，需实测。
- `TowerResources.ts` 包装资源队列；音频有独立路径。未来统一统计时不能漏算音频与渲染器自己的引用。
- `TowerView.ts` 进战斗预加载多个技能类，包括阵法、一剑开天等。应根据真实可用技能与依赖评估必需集合，不应简单把全部 preload 删除。
- `TowerDepthOrder.ts` 对子节点 slice、sort，再逐个 setSiblingIndex；可研究复用数组与仅提交变化次序，保持原比较规则。
- `TowerView.ts` 每次绘制清理/重画多个 Graphics，并临时过滤 effects；`TowerRun.js` 存在多处目标筛选与排序。它们是采样候选，尚未证明是主瓶颈。
- `LiangyiFormationArt.ts` 已有槽位复用和时间键：每阵地面 512×512、空中 768×1024，30 Hz 更新，并在脉冲变化时即时更新。两张完整 RGBA8 上传合计 4 MiB；按每秒各上传 30 次，理论像素量约 120 MiB/s/阵。不是实测总线带宽，实际由驱动与触发次数决定。
- `TowerLevelBeamArt.ts` 已用 384×768、30 Hz、时间键去重，动态图 packable=false。不能把已有措施再次计为新收益。
- 两仪、四象、突破、小境界光柱的画布创建分支依赖 wx 或 document；原生运行的等效能力必须验证，失败时不得静默退回缺失特效的版本。
- 御剑流光当前加载 v3、妖猪加载 v3、持握武器加载 v2；资源目录仍存在部分旧版本。仅凭文本搜索不足以安全排除，须检查动态路径、场景 UUID、元数据及构建依赖。
- 字节级完全重复图发现一组：`orbit-sword-v1.png` 与 `liangyi-v3/sword-white.png`，仅约 39 KiB；不应宣称去重能直接节约几十 MiB。

尚未测量：目标手机 FPS、帧耗时分位、CPU/GPU 瓶颈、首次下载量、解码峰值、APK 大小、TapTap 容器行为、热降频。方案中的后续指标均为拟定目标。

## 3. 保真红线与验收基准

1. 原始图片、视频、付费生成文件、不满意版本、生成记录全部保留。将不使用的版本移出发行清单不等于删除归档。
2. 不降低原生帧分辨率，不删除有效动画帧，不压缩前摇/命中/收招/消散时间；不减少剑、粒子、尾迹数量来换性能。
3. 技能颜色、透明渐变、叠加亮度、轨迹、范围、层次、震屏、音效与触发时机保持。已有“减弱动态”选项保持原语义，不能暗中作为低配模式。
4. 普通怪、Boss、狂暴分别验收；Boss 基础体型、狂暴完成后变红并放大 20%、结束/死亡恢复、脚底锚点、标签与裁剪遵守规范 65。动画源至少 256px，按实际显示像素检查。
5. 物品/道具/装备/武器静态图标保持 128px 中主体最长边 125px 的现有标准；角色、场景、特效、技能图不套用该规则。
6. 不改变战斗 tick、目标排序、碰撞、命中次数、随机数消费、伤害、掉落与存档语义。存档失败原子性、重复领奖校验仍是必须通过的门槛。
7. 只剔除完全不可见且无外溢影响的绘制；离屏敌人继续参与逻辑，不丢失尾迹、屏外进入的攻击、预警与光晕。当前视口本身参与战斗边界，禁止为了减少绘制去改逻辑视口。
8. LOD 不作为本期降低可见画质的手段。采用不可见绘制剔除、静态缓存和完全等价计算；若收益不足，重新评估最低设备，不默认删效果。

保真分两档：资源无损处理要求解码 RGBA 一致；渲染实现替换要求固定种子、时间与相机下逐帧对照，先标定同设备重复渲染噪声，再确定差异容限。全图平均相似度不能掩盖丢剑、预警缺失、透明边缘断层。关键效果 ROI 单独验收并看完整视频。

## 4. P0：平台与性能基线（预计 2–3 人日）

### 平台验证

- 从当前源码生成可追溯基线，记录源码内容摘要、引擎版本、构建配置和资源清单摘要。现有工作区有大量未提交修改，不以 HEAD 代替实际源码，不顺手提交其他工作。
- 验证 TapTap H5 候选：目标容器中横屏、安全区、输入、声音、存读档、切后台、动态画布、纹理上传、缓存均正常。
- 安卓原生最小验证：启动宗门、进塔、妖猪狂暴、两仪/四象、大小境界突破。记录 Canvas 能力与渲染结果；缺少能力时估算改用 Cocos 节点/网格/材质或原生绘制桥接的成本。保留 Web 作为参考，不生成另一个游戏逻辑分支。
- 决策：H5 真机达标且接入可行，优先它；若容器限制阻碍完整效果/性能，选原生并纳入特效等价适配；普通小游戏仅在确认其运行环境与适配器后列为候选。最终正式路线写入决策记录，后续指标只认该目标。

### 测试设备与场景

选实际可获得的低档、中档、高档安卓手机，覆盖不同 GPU 系列。记录型号、SoC、内存、系统、容器/浏览器版本、物理渲染分辨率、温度、刷新率。P0 确认具体机型和最低支持设备；不能只按内存容量归档。桌面用于诊断，不作为上架性能结论。

场景固定种子、装备、技能等级、输入脚本、时长与计数：冷启动宗门；全页面往返；首次进塔；普通战斗；实际合法配置中最密集的波次；御剑与多种大技能组合；两仪/四象叠加；Boss 狂暴及死亡；突破成功/失败；背包/技能页暂停恢复；连续 30 分钟游玩。额外超上限压测独立标记，不混同正式玩法。

指标按段采样：模拟、表现同步、Graphics、排序、纹理上传、提交/呈现；记录帧时间 P50/P95/P99、>33.3ms 和 >50ms 帧、长卡顿、资源请求/命中、纹理数量/尺寸、节点和池高水位。支持 GPU 采样则记录，不支持时明确留空，不能用 CPU 时间冒充 GPU 时间。

## 5. P1：发行资源瘦身（预计 2–3 人日）

### 5.1 可追溯发行清单

生成逻辑资源 ID → 源文件 → UUID/依赖 → 实际使用处 → 发布产物的清单。把资源分为必需、按需、历史归档、待确认；动态路径用显式注册表/测试覆盖补齐。运行访问记录是辅助证据，没访问到不代表不用。

首批候选：旧妖猪图集、旧御剑流光、旧持握武器、已替换试制图及误入资源目录的系统文件。先验证无引用并确认归档 hash 与恢复路径，再从导入/发布目录迁出。保留必要 .meta/UUID 信息，不破坏现有引用。构建图和全流程加载测试通过后计入节约量。

### 5.2 无损处理与共享

PNG 优化只允许同像素重编码；每张比较解码 RGBA、尺寸和透明通道。先在高占比样本测收益、导入耗时与运行解码耗时，再批量执行。无损格式转换也要验证目标环境支持与解码峰值；不预设一定更好。

相同文件可共用一个资源，但须同时验证采样、材质、引用计数和释放行为。图集裁透明边只有在重建原画布、frame rect、offset、脚底锚点和滤波扩边仍能保持表现时采用；不自动旋转帧、不缩放帧、不改变物品图标画布标准。

不默认启用 ASTC/ETC 等有损 GPU 压缩。可作为后续独立实验，以用户保真要求为准，绝不能仅因显存数字变小就接入。

### 5.3 发布与仓库分开

design、reports、历史证据保留；通过发布白名单阻止其进入产物。构建缓存与临时文件清理只改善开发磁盘，不计为玩家下载收益。只有可再生且无唯一素材的缓存才可另行清理。

交付：清单、归档映射、逐文件节约表、同像素校验报告、同源码重新构建的前后对照。体积缩减幅度待审计，暂以“尝试降低运行资源体积 10–20%”作为探索目标，不作为保真之外的硬指标。

## 6. P2：资源加载与内存生命周期（预计 3–5 人日）

按逻辑用途划分启动公共、宗门页面、共享角色、楼层怪物、技能族、突破、藏经阁图像资源组；不机械按文件夹切包，避免共享资源被复制。具体 Bundle 粒度由依赖清单决定。

- 启动只准备首屏必需项；进塔准备当前楼层所有波次/Boss、当前技能及可能即时触发的依赖。技能升级、新学技能、换装、读档也必须补齐依赖；首次技能不许空放。会在战斗中自动触发的成长依赖提前纳入可达技能集合；主动学习/换装在现有暂停或页面切换阶段完成准备后才允许恢复战斗。若动作尚未提交，失败保持原状态并重试；若已持久化，保留已提交状态并停留现有暂停界面重试，不重复扣费或回滚存档。不能延迟已发生的技能、推进无表现的战斗或重新弹出战斗全屏加载页。
- 将“本层必须”“下一场景预测”“可选后台”分优先级，限制下载/解码并发。分帧绑定纹理与节点，重负载战斗期间不做无边界预热。
- 继续使用已有加载队列和场景阻塞语义，防止战斗中背景加载再次弹全屏加载页。维持超时、重试、去重与依赖等待；过期场景回调不能绑定到新页面。
- 扩展 scope/lease：每个页面/战斗持有自身资源租约；共享项引用计数；未使用项可进入有字节上限的缓存。引擎 ImageAsset、渲染器 Texture2D/SpriteFrame、队列引用分别记账，确保释放顺序；严禁 releaseAll 误伤活跃资源。
- 同一 ImageAsset 可被不同 Art 类构造成多份纹理，需先查实际实例，再统一满足相同采样/颜色设置的纹理。池化节点隐藏不代表纹理已释放。
- 原生若选择本地内置核心素材，加载优化仍针对解码/上传与内存；H5 若采用远程资源，记录网络字节、缓存命中、版本摘要、失败重试。远程化只是转移下载时机，不算总资源减少。
- 可选缓存只删本游戏管理的缓存空间，不删存档。热更新必须资源版本一致、失败可恢复旧清单；不在本期顺带实现整套热更新平台。

交付：资源组清单、所有权图、加载状态机、加载/失败/切换回归、20 轮宗门↔进塔↔页面往返后的纹理与内存曲线。额外覆盖 H5 WebGL 上下文丢失/恢复与原生切后台/低内存后的资源重建；按原时间点恢复动态纹理，不重放伤害、奖励或已播放音效。P5 在目标环境复验。

## 7. P3：表现层优化（预计 3–5 人日）

### 第一优先：消除重复工作

HUD 的文本、图标、进度条只在值或布局变化时重算，移动元素仍正常更新；静态背景、边框与场景结构缓存。不能缓存会随时间变化的预警/光效为静态图。

保留地面深度比较规则，复用排序数组，仅 sibling 顺序变化时提交；透明对象不为了合批跨越角色、预警或其他特效重排。先测 draw call 与 CPU，再选静态图集，不把全部大图塞进一个常驻超大图集。

盘点现有对象池（伤害数字、阵法槽位等），在缺失且频繁创建的节点上补池化。池归还必须清掉事件、引用、定时器、命中标记和旧状态，设置可回收高水位；池满时扩容/调整预热，不能悄悄丢掉应显示的效果。

缓存稳定组件引用、颜色常量与临时缓冲；别把场景切换才执行一次的代码当成热路径优化。

### 第二优先：动态纹理热点

先测两仪、四象、突破、光柱的画布绘制/上传时间及同时活跃数量。它们已有 30 Hz 与暂停去重，本期不降成 15 Hz，也不减小纹理。

优先只更新发生变化的图层；能复用的静态部分使用既有图片/网格。若仍是主要瓶颈，将同样的剑、光点和阵纹编排转为 Cocos 节点/网格/材质在 GPU 上移动，保持原时间采样、轨迹、叠加与颜色。每个效果单独开关、独立验收，原实现保留作对照和回退。

局部纹理更新、共享动态结果仅在目标平台确实支持且输入/相位相同时采用；不把不同脉冲、目标命中、随机轨迹的阵法错误共享。预烘焙整段大特效可能显著增加资源量，不能未经测量就替代程序绘制。

交付：热点前后采样、节点/上传计数、逐技能对照视频及截图、长期运行结果。只有明确改善的变更才保留。

## 8. P4：战斗核心热点（条件阶段，预计 2–4 人日）

只有 P0/P3 证明战斗模拟是热点才执行，避免将本次变成重写战斗系统。

候选：筛选用缓冲复用、每 tick 空间索引、重复几何量缓存、目标查询复用。空间查询只缩小候选，最终距离/扇形/线段判定、排序与上限保持原逻辑。同优先级的 ID 顺序不能变；敌人移动、生成、死亡后索引及时更新。

不得降 AI 频率、增大模拟步长或跳过离屏敌人。对象池复用逻辑实体比表现节点风险更大，优先不做。优化随机采样与数组操作时保持随机流与副作用次序。

使用同一初始存档、种子、输入、tick 数，比较每 tick 的血量、蓝量、位置、目标、投射物、命中日志、掉落、随机状态与最终快照。跨平台浮点容限单独论证；计数、ID、奖励和时序不允许模糊容限。

## 9. 拟定验收指标

以下是专项内部目标，不是 TapTap 平台要求。P0 在最低设备与同内容基线确定后锁定，不能用修改画质来达标。

| 维度 | 拟定目标 / 判断 |
| --- | --- |
| 画面与技能 | 所有保真红线通过；每个改动效果有实机对照 |
| 帧率 | 最低支持设备正式玩法以 60 FPS 为目标；记录完整帧间隔分布，不用平均 FPS 代替稳定性 |
| 耗时 | 工作耗时 P95 尽量 ≤16ms；呈现间隔 P95 ≤18ms、P99 ≤33.3ms；区分测量口径 |
| 卡顿 | 预热后正式压力场景无可复现 >100ms 优化相关卡顿；>50ms 帧尽量减少且相对基线不回退 |
| 首次加载 | 同网络/设备/内容下，若存在过量加载，目标减少首屏必需字节 ≥30%、等待 P95 ≥25%；不牺牲首次效果完整性 |
| 安装版启动 | 单独统计进程启动至可交互、进塔时间；不拿 H5 下载时间比较 APK 本地启动 |
| 内存 | 若存在无用常驻，目标峰值下降 ≥20%；绝对 PSS/纹理预算由 P0 真机确定，不把纹理估算当进程内存 |
| 长期驻留 | 暖机后 20 次往返，活跃资源数回到应有集合；空闲后受控资源字节无单调增长；PSS 波动结合 GC/驱动解释 |
| 热稳定性 | 30 分钟正式密集玩法，最后 10 分钟仍达到锁定的帧时间目标；温度/亮度/供电条件一致 |
| 正确性 | 优化相关测试全部通过，存读档/失败原子性/重复领奖/暂停与恢复通过；无新增缺图与过期回调 |

相对改善目标仅针对基线中确有问题的维度；若已达标，不强求百分比。达不到时明确原因、保留画面、重新选择路线/最低设备，不私自降低目标或删效果。

每个代表场景先暖机，再采样至少 3 次，每次 3 分钟；冷启动单独跑至少 5 次。前后使用同设备、同运行环境、同帧率上限、同物理分辨率和同内容摘要。30 分钟压力另做。区分调试构建、性能采样构建与最终发行构建；正式结论来自发行配置。

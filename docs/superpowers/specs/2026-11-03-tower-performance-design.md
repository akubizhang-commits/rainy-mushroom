# 栖云宗：TapTap 普通小游戏保真瘦身与性能优化设计

版本：v2，2026-11-03。状态：设计方案，未实施游戏优化或平台接入。

## 1. 已确定的方向

用户已选择本期先做 **TapTap 普通小游戏**，个人开发，以后希望变现；保持素材清晰度、技能效果与横屏玩法。该决策替代 v1 的“H5/安卓安装版待选”路线。

本期只维护 TapTap 普通小游戏正式目标和 Web 内部对照环境。安卓 APK、Steam、TapTap H5 和微信发布不纳入。官方 Cocos 插件使用微信小游戏构建作为转换输入，仅复用工具链，不做微信上架，也不套用项目原微信发布预算。

目标按顺序为：**完整运行和可测量 → 首次进入少等 → 常驻内存有界 → 战斗稳定 → 广告前后不退化**。沿用 Cocos Creator 3.8.8、`js/xianxia` 战斗核心与已验收素材。

商业相关范围仅为平台广告适配边界、测试广告及暂停/恢复性能验证；不借本次优化上线付费、制定正式广告奖励、修改经济、增加强制广告或搭建完整商业后端。测试奖励使用隔离测试账本，正式经济规则另立项。

## 2. 当前基线与证据口径

沿用同日第一轮磁盘清单 `reports/web-performance-planning-2026-11-03/inventory.json`，不是本次 Tap 构建实测。后续源码/素材继续变化时必须重新生成，不可拿此旧清单当发布证明。

| 当前资源 | 文件体积 MiB | 首要动作 |
| --- | ---: | --- |
| 怪物动画 | 37.00 | 审计旧版图集、按本层物种准备、释放离场资源 |
| 技能特效 | 27.31 | 审计旧版、建立可达技能依赖、分析动态上传 |
| 宗门场景 | 20.78 | 首屏与其他院落分开准备 |
| 藏经阁物品图 | 18.36 | 索引与图片分离，可见条目优先 |
| 突破素材 | 5.43 | 按突破阶段准备，仪式结束释放不再使用项 |
| 角色素材 | 4.14 | 保留原分辨率，排查重复纹理 |
| 全部 resources（不含 .meta） | 123.06 | 按实际发行依赖审计 |
| 现存 Web 构建目录 | 131.18 | 仅作历史磁盘对照，不是 Tap 包或首屏下载 |

前四项约占资源总量 84%。364 张 PNG 全部按 RGBA8 基础层展开约 659.23 MiB；这是容量模型，不是实测内存。妖猪 v3 常态与狂暴图各 4096×3072，基础层各 48 MiB；两张同时驻留为 96 MiB，仅优化 PNG 文件大小不会让这部分像素占用同步下降。

已检查的热点候选：

- `TowerAssetQueue.ts` 在宿主寿命内持有完成资源；缺少场景粒度的驻留策略。
- `TowerResources.ts` 包装资源加载，音频走独立路径；需要补全所有权统计。
- `TowerView.ts` 入场预加载多个技能类，每次绘制会重建部分 Graphics 和临时集合。
- `TowerDepthOrder.ts` 每次复制排序并逐节点设置顺序；必须保持现有遮挡语义。
- 两仪已有 30Hz 和槽位复用，512×512 地面与 768×1024 空中图层完整上传约 4MiB/次，按 30Hz 为理论 120MiB/s/阵；不是实测带宽。
- 两仪、四象、突破、光柱的 Canvas 路径依赖 wx/document；需要 Tap 适配与真实能力检查。
- `TowerPlatform.ts` 已有部分生命周期接口；`PinePilot.ts` 仍直接读取 wx 安全区。
- 当前广告关闭；构建脚本没有 Tap 目标。没有 Tap 真机帧率、首包、网络字节、峰值内存或广告性能数据。

## 3. 平台约束与技术取舍

2026-11-03 已阅读官方 Cocos 适配、小游戏配置、分包、性能、CDN 和激励视频文档。来源在第 13 节。

1. Cocos 插件支持 3.8.x 及以上，先标准小游戏构建后转换 Tap 产物。记录插件版本、下载来源与校验值，不默认升级引擎。
2. 普通小游戏不原生提供浏览器 BOM/DOM；引擎适配器可模拟部分接口，自定义动态画布、文档事件、声音恢复仍需专项验证。
3. 最终 `game.json` 明确设置 `deviceOrientation: landscape`；Tap 分包字段是 `subPackages`，不可直接复制原微信打包输出的字段和加载路径。
4. 官方说明不同分包不可直接互引脚本或资源。**逻辑资源分组不等于平台分包**；最终映射由转换后依赖审计和最小加载试验决定。
5. Tap 的专属 CDN 文档只对部分合作游戏开放。默认先验证平台分包分发，不依赖专属 CDN；如因实际限制必须外置资源，另核验自有 HTTPS 资源部署能力、费用、缓存与版本完整性，未明确前不部署或付费。
6. 不把 Unity 文档中的尺寸建议、原微信 4/20MiB 项目预算当作本项目 Tap 硬限制。主包、分包、总包、缓存限制由 P0 核验本项目所用插件与上传渠道后录入，并标明来源/日期；未核验不得写“可上架”。
7. 激励视频官方描述为生命周期单例，创建后自动拉取，关闭后自动准备下一份。只建立一套应用级监听与一个在途请求，不能按每个按钮反复创建实例，也不能承诺完全控制平台自动加载时机。
8. 不默认上 Worker/WASM。官方 Worker 能力与主线程不同；仅在证据证明纯计算热点且序列化代价可控时再立实验，不把 Canvas 绘制直接搬到 Worker。

## 4. 保真与行为红线

- 所有原稿、原视频、付费文件、失败版本及生成记录保留；“不发行”与“删除源文件”分开。
- 不缩小原生纹理/帧，不删动画帧，不减少剑、粒子、尾迹和命中特效，不降低现有动画/动态画布更新频率。
- 颜色、透明渐变、混合亮度、轨迹、前摇/生效/收招、范围、震屏、音效、画面层级保持；现有减弱动态选项语义不变。
- 怪物遵守规范 65：普通/Boss/狂暴分别验收，源动作至少256px，Boss基础尺寸和狂暴20%放大、发动完成变红、到期/死亡恢复、脚底和标签保持。
- 物品/道具/装备/武器静态图标遵守原 128px 画布、主体最长边125px；角色、场景、技能图、特效不套用此规则。
- 不改变模拟 tick、随机数消费、目标排序、碰撞、伤害、掉落、奖励、暂停或存档事务语义。离屏裁剪只省绘制，不能省逻辑或改变战斗视口。
- 资源处理以解码 RGBA 一致为门槛；PNG 调色板减色、TinyPNG/pngquant 等有损处理不列为默认方案。ASTC/ETC 也不默认接入。
- 渲染实现替换固定种子、相机、模拟时间和设置，关键 ROI 与完整视频同时对照；相似度分数不能替代剑数量、命中时序、锚点和预警可读性检查。

## 5. 目标架构

```text
js/xianxia：战斗、成长、存档事务（保持独立）
           ↓ 状态与事件
Cocos 表现层：角色 / 怪物 / 特效 / UI
    ├─ TowerPlatform：生命周期、安全区、存储、时钟、画布
    │       ├─ Tap 实现（正式）
    │       └─ Web 实现（对照）
    ├─ TowerResources：逻辑资源解析与租约
    │       ├─ 发行清单：版本、路径、依赖、文件字节与像素字节
    │       ├─ 平台分包就绪 → Cocos Bundle/Asset 就绪 → 纹理绑定就绪
    │       └─ 活跃资源 + 有界空闲缓存（共享计数）
    ├─ 暂停协调：用户暂停 / 后台 / 广告 / 资源恢复
    └─ 测试广告控制器：单例、请求代次、测试收据
```

`TowerView` 只提出进入页面/战斗所需的资源集合，不知道资源部署地址；各 Art 类通过 scope 取得资源、纹理和帧。平台广告回调不直接修改战斗、背包或结算。

### 5.1 逻辑资源组

| 组 | 内容 | 取得时机 | 释放规则 |
| --- | --- | --- | --- |
| boot | 引擎、入口、加载/重试 UI、首屏必要图文 | 启动 | 入口与错误恢复保持可用 |
| camp-current | 当前宗门院落、可见 UI | 入宗门/切院落 | 离场解绑后可进入空闲缓存 |
| player-common | 当前角色、当前持握装备、通用反馈 | 首次需要 | 所有使用者释放后才可回收 |
| battle-floor | 当前层全部波次、Boss、机制与掉落依赖 | 进层屏障内 | 离层且死亡/消散尾部结束后 |
| skill-reachable | 当前技能与本段可能自动触发的技能依赖 | 进战斗/已有暂停界面 | 相关技能与在途效果均结束后 |
| ritual | 本次突破完整仪式资源 | 进入现有突破界面时 | 仪式和尾部结束、无共享者时 |
| library-visible | 当前页/筛选结果可见图像 | 打开列表、滚动时 | 不可见项退出有限缓存 |

当前层要加载什么以游戏配置与清单计算，不能手写“第一关只加载妖猪”。共享怪物和技能按资源 ID 复用；不把同图复制到每层。

### 5.2 物理交付策略

默认：主包保留控制代码与 boot；重资源由资源型平台分包承载，入口为最小注册代码。先验证主包控制器加载两个独立分包及其 Cocos 资源的可行性。不同分包不能直接引用彼此。

构建审计将跨分包依赖报告为错误；可采取同一依赖闭包合并、将少量共享项放主包并验证可访问性，或用已验证的主包资源服务解耦。**不靠复制所有共享大图消除错误。** 若插件不能实现某种拆分，优先合并该闭包并报告首战字节代价，不能编造按技能独立下载的收益。

P0 固化物理包表后才移动资源；逻辑 scope 仍可在大物理分包下载完成后只解码/绑定其中当前需要的图片。下载完成、资源解码、GPU就绪三者分别计量。若最终首战必须下载较大闭包，指标如实体现，不把“首屏小”当“首战快”。

## 6. 资源瘦身与生命周期设计

### 6.1 瘦身顺序

1. 生成运行引用清单（代码静态路径、动态注册、场景 UUID、.meta、Cocos依赖与运行记录）。
2. 检查旧妖猪/旧御剑流光/旧持握武器等候选。确认无正式引用、原件与 hash 已归档后，仅移出发行导入路径，保留 UUID 对照与恢复位置。
3. PNG 小批无损重编码，逐文件比较 RGBA、尺寸、透明通道，测压缩量和解码耗时；有收益才批量。
4. 完全相同且采样/色彩语义相同的图共用一份。已知字节重复只有约39KiB，不能预报大额去重收益。
5. 小 UI 图集按共同使用场景组织，不将所有大图合成常驻巨图。裁透明边必须可重建原画布/锚点/滤波边界；不旋转帧、不缩帧、不破坏图标125px主体规则。
6. 发行白名单排除 design/reports/源视频/开发缓存；开发磁盘清理收益不计入玩家包体收益。

### 6.2 加载调度

优先级为：当前屏障必需 → 明确下一场景预测 → 可选后台。下载、解码/纹理绑定、平台自动广告加载分别记录。建议初始应用可控下载并发2、纹理绑定每帧最多1个大资源任务；这些是实验参数，P0/P2按实机调优，不保证单次上传不会超过帧预算。

重图解码/上传尽量在场景准备屏障内完成；超过屏障允许的资源只作为后台项，不重新打开战斗全屏加载页。现有两帧准备机制保留为最小条件，并增加“必需依赖已完成且所有关键绑定成功”，不能只等两帧就判就绪。

首屏后的预测下载可利用宗门停留时间，但进塔不能强迫等待人为倒计时，也不能为了命中预测提前解码所有未来楼层。小游戏后台不持续跑预取循环。

### 6.3 引用、回收与失败

资源租约包含 `(buildId, logicalId, type)`；一个资源可以被多个 scope 持有。ImageAsset、共享 Texture2D、SpriteFrame、节点绑定及动态 Canvas 分别统计，释放顺序先解绑再销毁派生对象，最后释放资源租约。

空闲缓存设字节预算，先驱逐零租约项；内存压力时暂停应用可控预取并清空闲项，不释放正在播放的Boss/技能。活跃集合本身超预算时输出诊断、停止新预取，不默默删效果或降画质。

切场景用 generation token 忽略过期绑定；失去最后等待者的在途请求即使无法取消，也只能清理结果，不能重新挂回当前界面。失败资源不永久占位，重试不重复下载已完成依赖；损坏缓存删除范围仅限本游戏资源缓存，不触碰存档。

版本目录不可覆盖旧文件；清单记录 buildId/hash/尺寸/依赖。代码与资源必须匹配，失败回退只可使用同代码兼容的完整清单。没有有效旧清单时保留加载重试界面，不能混用版本或带缺图进入战斗。此次只实现随发布版本固定的清单，不增加远程代码热更新。

### 6.4 技能资源就绪

进场提前覆盖所有可能自动生效的技能及升级外观。主动学技能、换装、读档在已有暂停/页面边界补依赖；未提交的操作失败保持原状态，已持久化的操作保持已提交状态并留在暂停界面重试，不重复扣费，不倒退存档。

突破资源在其已有准备界面等待；确认资源就绪后才开始可见仪式。不能因资源迟到延长战斗内已发生的前摇/命中时间。战斗遇到本应必需但未登记的资源，记为清单缺陷，修清单后验收，不能用缺失效果回退掩盖。

## 7. 渲染与计算优化

### 7.1 第一轮：保持实现形态，减少重复工作

- HUD 值不变时不重写文本/进度几何；静态场景几何缓存，与跟随相机的变换分离。
- 深度排序复用工作数组，比较规则不变，仅次序变化时提交 sibling index；不为合批打乱透明叠加顺序。
- 节点、组件引用、稳定颜色和临时数组复用；补足热点对象池的重置/销毁路径，池高水位有记录，容量不以丢效果控制。
- 裁剪只针对完全不可见且无外溢的绘制，尾迹、预警、震屏相关元素保留。
- 同样像素且相同采样设置的 ImageAsset→Texture2D 只创建一份；动态纹理保持 `packable=false`。

### 7.2 第二轮：仅处理采样证明的动态纹理热点

两仪、四象、突破、光柱分别采样绘制/上传/绑定，不合并为含糊的“特效慢”。现有30Hz、时间键和暂停去重保留。

先分离真正静态图层；仍超预算时，只对该效果试验 Cocos Sprite/网格/材质编排，保持轨迹、数量、相位、混合和原采样时序。跨效果不共享不同命中/脉冲状态。每个效果留原实现对照开关，实机保真通过后再移入发行默认路径。

不将所有动态特效一次性改 Shader，不默认烘焙成大视频/图集。若 Tap Canvas 能力不足，这一步属于必要平台适配；工作量在 P0 单列，而非靠静态占位宣布成功。

### 7.3 战斗核心为条件项目

只有模拟成为热点才优化 `TowerRun.js` 的目标筛选/几何查询/临时集合。保留目标排序、距离判定、随机流与每 tick 副作用；先做确定性回放对照，再考虑空间索引。不上网络战斗、不降AI频率、不改dt、不减少正式敌人数。

## 8. 广告与前后台的性能边界

本期只接一个测试激励入口，使用测试位与隔离存档，不向正式存档加奖励。

- 一个应用级广告控制器，按 `uninitialized/loading/ready/showing/failed` 记录状态；监听一次，显示请求串行，取消/失败不产生测试奖励。
- 首屏必需资源就绪、允许的初始化条件满足后再首次创建。创建会自动拉取，关闭还会自动准备下一份，因此应用只限制自己的资源预取，不能假设平台广告网络任务可暂停。
- 广告显示前保存已有稳定检查点，获取广告暂停原因，清输入、停游戏音频/动态纹理更新；保持当前活跃纹理，不为广告主动卸载整个战场。
- 多原因暂停包含 user/background/ad/resource-recovery；每次获取返回带场景generation的独立所有权令牌，只能幂等释放自己的令牌。同原因多个任务按令牌计数，不能一个恢复任务结束就清掉另一个的暂停。只有全部令牌释放、原场景仍允许运行且关键绑定就绪，才可恢复。广告关闭只释放其ad令牌；用户暂停、应用后台或纹理未恢复均不自动开始战斗。系统onShow不等同广告结束，过期回调不得释放新场景令牌。
- 关闭结果只有 `isEnded===true` 才形成当前请求的测试收据；重复回调只处理一次。创建/加载失败或show在真正展示前拒绝，立即回收该请求自己的ad令牌，不影响其他暂停。已展示但关闭回调缺失时，超时不主动关闭视频、不伪造完成、不按onShow推断结束；保持暂停并记录可恢复错误，只有经已验证的平台结束信号确认后才解除ad令牌。若平台无法提供确认路径，允许退出并从稳定检查点重新进入，旧测试请求作废、不发收据。没有可靠完成凭证的闪退恢复不猜测发奖。
- 纹理丢失后按原模拟时间重建；已有暂停页内呈现恢复状态，待绑定就绪再允许继续，不补跑隐藏期间的 tick，不重播命中/音效/奖励。
- 测量广告请求、显示、关闭后首个完整游戏帧、恢复可操作时间和30/60秒内存变化；平台自动缓存与游戏自有泄漏分开记录。SDK自身内存无法逐对象观测时明确标记未知。

正式奖励、防作弊、服务端验证、广告次数与定价不在本优化项目实现；以后沿独立商业事务接入，不在渲染回调里改背包。

## 9. 指标与验收方法

### 9.1 内部优化目标（不是平台硬限制）

| 维度 | 设计目标 |
| --- | --- |
| 主包 | 尝试控制在12MiB以内；先实测，无损无法达到时报告组成与原因 |
| 全资源 | 在真实引用审计后争取减少10–20%；不承诺删除未确认素材 |
| 首屏/首战 | 分别统计所需下载字节与等待；存在过量加载时争取首屏必需字节降30%、等待P95降25% |
| 渲染帧率 | 最低已确认支持机型正式玩法60FPS目标；不通过降分辨率达标 |
| 帧耗时 | 主线程工作P95尽量≤16ms；呈现间隔P95≤18ms、P99≤33.3ms，区分统计口径 |
| 长卡顿 | 预热后无可复现的优化相关>100ms卡顿；记录>50ms帧而非只报平均FPS |
| 内存 | 有无用常驻时争取峰值降20%；绝对纹理/进程预算在P0机型基线后锁定 |
| 重复进出 | 暖机后20轮进塔/宗门/菜单，受控活跃资源回到应有集合，零租约缓存有界 |
| 广告恢复 | 前台且资源未丢失时，关闭后恢复到原界面可操作目标≤500ms；重建单列，目标≤2秒 |
| 热稳定 | 30分钟密集正式玩法，末10分钟仍满足锁定帧目标，不崩溃 |
| 保真/正确性 | 图像/完整技能/暂停/存读档/失败原子性/重复领奖全部通过，无新增回归 |

12MiB、百分比与恢复耗时均为项目目标；不能因不达标自行降低素材清晰度。P0 锁定具体机型、预算与可测量方法后才作为执行验收合同，测不到的指标不伪造。

### 9.2 测试矩阵

性能主验收先选3台实际安卓设备（低/中/高档，覆盖不同GPU），记录型号、SoC、RAM、系统、Tap版本、刷新率、物理渲染分辨率、温度和供电条件；最低机型待P0确认。iOS不是默认首发承诺；如平台实际发布覆盖iOS，则增加iOS真机验收后才开启相应范围。Web只作功能与视觉对照。

每个3分钟场景暖机后至少3次，冷启动至少5次；相同种子、技能/装备、输入、分辨率和发行配置。分别测空缓存、热缓存、20Mbps/80ms延迟与受限网络5Mbps/150ms延迟；实际无法限速时注明条件，不将估算混入实测。使用测试广告，不反复展示正式广告刷数据。

场景包括：宗门首屏、所有院落、藏经阁滚动、第一次进塔、合法最密集波次、满组合技能、两仪/四象重叠、普通/Boss/狂暴与死亡、突破成功/失败、技能切换、广告完成/取消/失败、后台与广告事件乱序、纹理恢复、慢资源、损坏缓存、存储写失败。

基线分两条：Web同内容用于原视觉/逻辑对照；Tap最低适配版用于性能前后比较。两者不能互相替代。若某特效在最低适配版缺失，则先完成等价适配再建立该效果性能基线。

## 11. 构建、配置与发布边界

拟新增 `taptap-minigame` 项目构建目标：同步共享逻辑 → Creator官方插件转换 → 校验Tap配置/依赖/资源 → 输出来源摘要和字节报告。

不先执行旧 `package-wechat.mjs` 搬目录再交给插件转换；Tap任务隔离输出，不污染现有Web/微信产物。原微信脚本保留其规则，Tap使用独立预算与验证。最终报告只能在本次全部检查通过后生成成功标志，避免旧3MiB报告掩盖当前超量产物。

发行产物不得携带其他平台SDK、源码地图或可改存档的调试入口；测试包可有显式测试入口与隔离存档，不能依赖浏览器query才可验收。密钥不进入客户端；TapAppID/测试广告位不编造，从实施环境注入。

本轮只设计，不安装插件、不创建平台应用、不上传包、不购买CDN、不生成新素材。

### H2 — 敌人数量裁定项未闭合（00 3–4 种 vs 01 5 种 + 精英 + Boss）
位置：00 §3 vs 01 §0、§9。
问题：00 §3 写“3–4 种虫群 + 1 精英/首领”，01 §0 改为“5 种普通 + 1 精英 + 1 Boss”并要求 00 同步，但 00 正文始终未改。两份“唯一依据”文档各执一词，00 §5 明确要求 M0 结束时“三份互相对齐、无待定二选一”。
影响：开发按哪份排期不明；04 的 bot 平衡阈值、05 的内容介绍文案（已写“蚊蚋、甲虫、灰蛾和蜗牛”四类 + Boss）都默认 5 种。
裁决建议：**采用 01 的 5 种普通（gnat/beetle/moth/snail/sporeling）+ elite_beetle + boss_mist_snail**。理由：本任务原始需求（用户 message 6 选“生存游戏”并要求 5–6 种内容的割草体验）、05 文案与 03 的 data/enemies.js 结构都已按 5 种展开；精英复用甲虫逻辑增量极小（已核实 03/01 一致）。改法：把 00 §3 的“3–4 种”改为“5 种普通 + 1 精英 + 1 Boss”，并在 00 §6 风险表或 §5 里保留 R-性能预案“真机不达标时按 01 §18.4 降同屏上限，不删种类”。

### H3 — 技能数量裁定项未闭合（00 6 主动+4 被动 vs 01 5 武器+6 被动）

### H4 — 存档 settings 字段三文档不一致（sound only vs +vibration/reduceFlash）
位置：01 §13.3、02 §0/§4.5/§6、03 §5.2、04 §1 Q1。
问题：02 §0 新增 `vibration`（默认开）、`reduceFlash`（默认关）两项无障碍设置，并在 §4.5/§10-8 要求“三项重启后保持”；但 03 §5.2 的 schema 1 `settings` 只有 `{sound:true}`；01 §13.3 只提“音效开关”。04 §1 Q1 已标出该冲突但只能“暂定”。三者未对齐，且这是会写进存档结构的硬字段。
影响：若按 03 落地，02 的减弱闪烁/震动开关无法持久化，02 §10-7、§10-8 验收用例必然失败；无障碍（02 §6）承诺落空。

### H5 — 存档写入失败的用户反馈，02 与 03 直接冲突
位置：02 §4.5 vs 03 §5.4、§10；04 §1 Q2。
问题：02 §4.5 写“设置项写存档失败不提示（StorageService 已兜底）”；03 §5.4/§10 明确不复用 StorageService，写失败时营地页提示“存档写不进去，本次进度不会保存”。两条是互斥的 UX 规则，且 02 的括注基于一个**已被 03 推翻的前提**（“StorageService 已兜底”——03 §1-4 说明新模块 SurvivorSave 不复用 StorageService）。
影响：UI 与表现层行为无法同时满足；测试用例预期相反。
裁决建议：**采用 03**（写失败要提示，设置页也适用，不止营地页）。改法：02 §4.5 把“写存档失败不提示”改为“写存档失败时按 03 §5.4 提示‘存档写不进去，本次进度不会保存’，但本次运行内仍按新值生效”；04 §1 删除 Q2。

### H6 — UI 素材图集分组与架构合批方案冲突（4 图集 vs 单图集）
位置：02 §8.2（4 张图集 actors/fx/ui/scenery）vs 03 §6.2“战斗中所有 Sprite 来自同一张 survivor 图集、同一材质”、§7.3 DrawCall ≤ 25；04 §1 Q3。
问题：02 把素材拆成 4 张独立图集；03 的合批前提是战斗层同层 Sprite 共用**同一张**图集（否则切图集打断合批，DrawCall 超标）。战斗层会同时出现 actors（敌人/角色）、fx（弹体/拾取物/底影）两类，分属两张图集，必然跨图集 → 合批被打断。02 §9-3 也把合批方案推给 03，但自己又先拆了 4 张图集。
影响：直接威胁 03 §7.3 的 DrawCall ≤ 25 预算与 T2 风险；是“UI 清单 vs 性能预算”的实质矛盾。
裁决建议：**战斗期实际参与渲染的 actors + fx 合并为一张图集**（scenery 可独立，因为地面是最底层单独批次；ui 只在模态框/HUD，不在战斗合批热路径）。改法：02 §8.2 把 survivor-actors 与 survivor-fx 合并为单张 `survivor-battle`（2048×1024 以内，RGBA ≤ 03 §7.3 的 8MB 纹理预算），scenery、ui 保持独立；明确“战斗层所有动态 Sprite 必须来自 survivor-battle”。同步更新 02 §8.1 的合计体积与 03 §7.3 纹理内存口径。04 §1 Q3 据此关闭。

### H7 — 05 运营埋点依赖的字段/能力缺少架构对应，首发“必带埋点”无法落地
位置：05 §0（“首发必须带最小埋点集”）、§5.3（通道【依赖 03】）、§5.4（事件表）vs 03 全文。
问题：05 把埋点列为**首发必备**（§0），但：(a) 上报通道、AnalyticsService 封装明确标【依赖 03】，而 03 全文没有任何埋点/上报/AnalyticsService 的设计（03 §8 只谈 MVP 后的云开发排行榜）；(b) 05 §5.4 的 `run_end.killer`（致命伤来源 id）、`levelup_offer.card_1..3`、`decision_ms`、`run_checkpoint` 的 hp_pct 等字段，需要逻辑层 SurvivorRun 暴露相应数据或事件，而 03 §3.1 的 `summary()` 字段里没有 killer，§3.7 事件表里也没有可直接映射 `card_x`/`decision_ms` 的事件。05 §9 Q4 把这些挂起给架构，但 00 §5 要求 M0 三文档对齐。
影响：若 03 不补，05 的首发埋点与 §5.5 的数据运营节奏全部悬空；“首发必带”与“架构未设计”直接矛盾。
裁决建议：二选一并写死——**(推荐) 把埋点降级为“首发尽力、依赖 03 M3 补设计”**，或**要求 03 增补一节“分析/上报接口”**。改法：若选推荐项，05 §0 把“首发必须带最小埋点集”改为“M3 评估接入，接口依赖 03 增补”，并把 Q4 列入 00 风险表跟踪；无论哪种，03 需补：`summary()` 增加 `killer` 字段，或在 §3.7 事件表新增 `levelUpOffer{cards}`、`levelUpPick{picked}` 两类事件供表现层转译为埋点。推荐同时在 03 §2 目录预留 `js/services/AnalyticsService.js`（与 AdService 同风格）。

### M2 — 分辨率/触控单位换算裁定项：策划假设仍挂起
位置：01 §4、§18.1（“若 UI 定为 750×1334 则等比换算”）vs 02 §0（锁定 720×1280 FIXED_WIDTH）、03 §1-1（720×1280 FIXED_WIDTH）。

### M3 — 刷怪半径公式：03 要求 01 同步，01 未同步
位置：01 §10（spawnRadius 写死“≈794”）vs 03 §1-2（改为按实际视口 `hypot(viewW/2,viewH/2)+60`，`relocateDistance=max(900,spawnRadius+120)`）。
问题：03 已核实指出，19.5:9 机型可见高度约 1560，01 的固定 794 会在屏内刷怪，并给出按视口计算的公式，明确“请策划在 01 中同步”。01 §10 仍是固定值 + “超过 900 重定位”。（已核实：720×1280 下 hypot(360,640)+60 = 794.3，与 01 一致；但高屏不一致。）
影响：高屏体验缺陷（屏内刷怪）；01/03 公式名义不一致。
裁决建议：采用 03 公式。改法：01 §10 把“半径 = 屏幕半对角线 + 60（720×1280 下约 794）”改为“半径 = hypot(视口宽/2, 视口高/2) + 60，由开局实际视口决定；720×1280 下约 794”；把“超过 900 重定位”改为“超过 max(900, 刷怪半径 + 120) 重定位”。

### M6 — 存档注入接口 removeItem 未被现有先例覆盖（03 自称“与 LibraryProgress 相同”）
位置：03 §5.1（“SurvivorSave 接收 {getItem, setItem, removeItem}，与 LibraryProgress 相同”）。
问题：已核实 js/library/LibraryProgress.js 只使用 `getItem` 与 `setItem`，**不使用 removeItem**；PinePilot 注入的 `progressStorage`（audit 场景，已核实）也只实现 `{getItem, setItem}`。因此“与 LibraryProgress 相同”的措辞不准确，且若 SurvivorSave 真的调用 `removeItem`，现有内存 Map 注入与 audit 注入会缺这个方法。
影响：按文档实现时，测试/浏览器/audit 场景注入对象缺 removeItem，若 SurvivorSave 在清损坏档时调用会抛错。

### M7 — package-wechat 分包追加逻辑与现有代码实际行为不符
位置：03 §7.5-2（“分包名单从 ['internal','main','resources'] 改为在存在时追加 survivor，按 assets/<name>/config.json 是否存在判断”）。
问题：已核实 scripts/cocos/package-wechat.mjs 当前对名单里**每个** bundle 做 `if(!existsSync(.../config.json)) throw`（第 11 行），即“缺失即报错”，并非“存在才追加”。03 的描述方向正确（需要让 survivor 可选），但现有函数结构是“固定名单 + 强制存在”，直接追加 'survivor' 到名单会在没有该分包的早期构建里直接抛错。03 没说清要改的是名单生成方式（从固定数组改为探测 assets/ 下所有含 config.json 的 bundle）。
影响：实现者若照字面“追加到名单”，会在 survivor 分包尚未建立的 M1 早期构建报错。

### M9 — 合规禁用词清单三文档不一致（“死亡/倒下”边界）

## 专项评估（任务点名项）

### MVP 能否在 2–3 个 Sprint 完成
基本可行，但 S1 偏重。03 §15 把 M1 拆为 8 步（sync-shared 对接 → 核心数据结构 → data → 全部战斗系统 + SurvivorRun → 分包 → 表现层 → 真机性能样板 → 存档）。01 §16 把 MVP 分 S1/S2/S3 三个 Sprint，与 00 §5 的 M1/M2 对齐。判断：

- **S1（M1）现实可达**：2 敌人 + 3 武器 + 升级三选一 + 失败结算，逻辑层纯 JS 可单测，占位美术用 Graphics，风险低。
- **S2 是最重的 Sprint**：一次性要加 3 种敌人 + 精英 + Boss（3 技能 + 狂暴）+ 撤离胜利 + 2 武器 + 6 被动 + 5 组进化 + 完整波次。建议项目经理把 Boss + 撤离与“被动 + 进化”再拆成两个子批次，否则 S2 验收（完整通关一局）易延期。
- **S3 调参不确定性最高**：依赖自动对局把通关率收进 30–60%、时长 6–9 分钟，可能需要多轮改数值（见 M10）。
- 结论：**3 个 Sprint 可完成 MVP，但需把 S2 内部再分批，并为 S3 调参预留缓冲**；2 个 Sprint 不现实。另：H1（04 残缺）会卡住 S1 的验收门槛定义，须先补。

### 是否违反核心约束（不血腥 / 不吃野生菌回血 / 不编造平台数值）
整体合规，设计上处处呼应约束，未发现违反：
- **不血腥**：01 §2、§9（净化为光点/水汽，无血/尸）、02 §7、§5.3（受伤为屏幕边缘晕影不画在角色身上）、05 §2/§3.2 一致。失败演出用 traveler-death 帧（已核实该帧集存在于复用素材）+ 灰蓝雨雾，无血。合规。
- **不吃野生菌回血**：回血来源严格限定露珠/露水叶片/露水祝福/撤离阳光（01 §2、§11、§5），蘑菇只作武器/外观/敌人（迷途菌灵）/装饰；05 §3.2 结尾甚至主动写“现实中请勿采食野生菌”。合规；且 03 §12 + 04 §7.1（待补）用禁用词扫描自动化兜底。
- **不编造平台政策数值**：05 全文把涉及平台/政策/资质的内容一律标【需以官方文档核实】，适龄年龄段、字数上限、流量主门槛、诱导分享规则均未给具体数值。合规。
- 唯一需盯：H1 补齐 04 §7.1 的合规扫描规则后，这条“自动化兜底”才真正落地；M9 的扫描边界需同步。

### 需求是否有歧义导致无法开工
S1（M1）范围**可以开工**：核心循环、摇杆（01 §4 数值完整）、2 敌人、3 武器、升级三选一、失败结算的数值与规则在 01 中齐全且已核实自洽（武器各档表、xp 公式、波次 0–3 分钟段、敌人表）。03 的接口（SurvivorRun、Pool、SpatialGrid）定义到可实现粒度。
但以下在进入对应 Sprint 前必须先裁定，否则该范围无法开工：
- H2/H3（敌人/技能数量）影响 data 模块定义——S1 的 data/ 要先知道最终清单（即便 S1 只实现子集）。
- H4（存档 settings 字段）影响 SurvivorSave schema——S3 存档开工前必须定。
- H6（图集合批）影响美术产出格式——M2 美术开工前必须定。
- H7（埋点）影响 S3/M3——可延后但要明确归属。
结论：**S1 可立即开工（在 H2/H3 裁定数量后），但 H1 必须尽快补以给出验收门槛**。

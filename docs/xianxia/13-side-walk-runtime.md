# 单侧步态修整与运行时接入

日期：2026-10-26。范围：修仙试玩人物表现；经典模式和战斗规则保持原样。

## 画面审阅与定点修改

v3 的主要问题是膝部外缘偏硬、脚掌在摆动阶段始终水平，以及衣摆和剑鞘缺少跟随。原画的脸、头发、服装与17层结构继续保留，不重新生成另一个角色。

v4 收顺膝部端盖轮廓，摆动脚增加最高12°的脚尖角度，衣摆与剑鞘分别加入约±3°和±2.2°的跟随运动。步幅由156源像素表达，另制作独立静止站姿。主线程检查了修改前后对比和八相位采样，未见明显断肢、重复肢体；布料折面和护腕接缝仍有精修空间。

## 接入边界

使用32帧行走和1帧站姿的透明图集，各帧96×168，整图768×840，统一脚底锚点(48,160)，名义角色高度80游戏单位。右侧采用同一侧面镜像；这不是八方向美术。

步态读取实际模拟位移与模拟时钟，不改变角色速度、碰撞、攻击或随机数。移动频率限制在1.4–2.0周期/秒，避免按短美术步幅直接换算高速倒腿。俯视游戏中的美术步幅与位移不严格相等，因此不声称实际游戏世界坐标中完全锁脚。

纯上下移动保持最近侧面方向；左右方向需要累计足够反向位移才翻转，避免微小抖动。资源错误时使用原人物回退。

## 验证记录

初版把walk与idle两个人物Sprite交叉淡化，独立QA发现半透明躯干与双腿轮廓，拒收。最终改为32个行走起点各4张收步姿势，单独768×2688透明图集；每张由原始17层关节插值、固定骨长IK重新渲染。约120ms收步期间只显示一个人物，不叠放两个姿态。最后一帧与idle可见像素一致。

最终验证：

1. `npm test`：557/557通过；`npm run check`通过；web-mobile重建成功。
2. 实际编译包21项断言通过，覆盖行走、反向、上下保留侧向、单人物不透明收步、暂停/升级冻结、恢复移动、无敌颜色、经典角色路径。
3. 实际Cocos加载方法另验2项：经典不请求角色资源；收步图集故障可回退旧角色。
4. 390×844窄屏实际Canvas键盘事件触发左、上、右移动和三次收步。此前两次测试将事件投递到window/document，未到达Cocos监听的GameCanvas，属于测试注入位置错误，保留失败记录；最终`canvas-input.json`通过。
5. 独立QA遍历32个收步起点，单人物、透明度、暂停、重新移动及资源失败检查通过；实际游戏录屏截取未见先前的半透明双腿。
6. 31个玩法JS文件哈希未变；运行时4个PNG/JSON与美术导出逐字节相同。未重跑完整平衡矩阵。

证据目录：[本轮报告与日志](../../reports/side-walk-integration-2026-10-26/)。新增控制器与图集解析为`SurvivorCharacterMotion.ts`、`SurvivorCharacterAtlas.ts`；`SurvivorBattleArt.ts`负责显示，`SurvivorView.ts`仅传入规则集加载开关。

## 限制与后续

当前只接入侧面行走、站立和收步，右向为镜像，上下仍用侧面。尚未制作独立施法、受击、正背面动作；精细布料和关节美术仍有提升空间。80u人物在390px宽屏上较小，不能把放大审图效果等同于真机辨识度验收。

新增两张人物纹理的RGBA像素合计约10.34MiB，尚未做微信构建、真机内存和长时间性能测试。原有平衡问题与敌弹容量问题不属于本轮人物表现修改。

本轮还记录了运行中从大视口改为390px后HUD字体异常放大/图集警告，重新加载恢复；截图`game-mobile-final.png`保留问题，`game-mobile-reloaded.png`是恢复结果。没有把这项窗口缩放问题混入角色改动，需单独修复。

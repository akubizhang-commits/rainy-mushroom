# 随机阶位妖丹：纯掉落模块

2026-10-28，已接入 `TowerRun`、`TowerCampaign` 与宗门塔界面。下文保留纯模块和接入方的职责边界；“父任务”指集成实现，不是尚未开发的功能。该规则覆盖旧的普通妖兽每20杀一丹规则。

玩家看到的是带阶位的妖丹，击杀时即按一阶折算入现有余额，界面称“妖丹值”。例如三阶一颗折合3点，仍属于同一种资源，不增加第四种货币。结算展示本次各阶颗数、折合值、独立的通层/首通奖；这些颗数是本次获得记录，不是尚未消耗的背包库存。技能书及研习的现有价格不变。

新开挑战保存独立 `loot: {version:1, seed}`，逐个击杀记录 `coreRank`，0代表未掉落。快照校验重建整层计划并核对每条记录；Campaign拒绝同一挑战更换种子/规则或改写已记账的阶位。已在进行中的旧挑战继续原规则，下一次新开挑战自动使用新版；不改旧余额、不重抽旧记录。Campaign仍为schema3，`lastResult.coreLoot`作为可选的本次颗数明细兼容旧结算。

- `CORE_RANK_VALUES`：冻结数组 `[0,1,2,3,4,5,6,7]`。一枚 N 阶妖丹向既有 `cores` 增加 N；钱包显示“妖丹（折合一阶）”，价格不变，不增加货币。
- `CORE_DROP_RULES[floor]`：冻结对象，每层字段为 `{floor,minCount,maxCount,minValue,maxValue,normalChance,eliteChance,bossChance,targetValue}`。
- `buildCoreDropPlan(floor, seed)`：floor 为整数 1–9，seed 为 uint32（含 0）。返回冻结普通对象，仅包含掉落的 `"wave:localId": rank`；未命中不存在该键。非法参数抛 `RangeError`。

逐次真实击杀只查询自己的键；命中一枚，阶位严格等于原型阶位，直接按 `CORE_RANK_VALUES[rank]` 入账。未杀、失败、退出、任意部分击杀不补足整层预算。父任务保存原始掉落 seed，恢复时用同一 floor/seed 重建，不采用已推进的 combat RNG，也不更换 seed。

一层编号来自 `FLOOR01.waves[].batches[].unit_ids`。二至九层按 `FLOORS[].waves[].enemy_groups`，Boss 组稳定排前，其余组保持编排顺序，然后每波编号 `u1...`。键不含 attempt 前缀；父任务从已验证的击杀实体取 wave/localId。模块只导入 `TowerContent.js`，不导入 `TowerRun.js`。

旧击杀目标为 `[63,65,78,87,90,108,105,110,119]`；首层实编排 372 普通、5 精英、1 Boss，因此 `floor(372/20)+5×5+20=63`。普通计数跨层余数会使旧实际收益最多相差 1，本表采用起始余数 0 的固定基准。清层额外 `5×(floor−1)` 和首通额外 10 均排除在击杀目标之外，父任务保持原有奖励。

候选概率：精英 0.65、Boss 0.9，普通概率按线性阶位总值校准，使未经条件筛选的期望正好等于旧目标。整层价值界为目标 ±10% 向内取整，数量界为候选期望数量 ±15% 向内取整。最多 16 次候选采样，全部失败后采用确定性可行预算构造；不会无限重抽。各实体在最终计划中相关，候选概率不是最终独立概率保证。

## 数值与通关总收益

设同层所有普通、精英、Boss 的阶位和分别为 `Vn, Ve, Vb`，则：

```text
p_normal = (targetValue − 0.65×Ve − 0.9×Vb) / Vn
E[count] = normalCount×p_normal + eliteCount×0.65 + bossCount×0.9
min/maxCount = ceil(E[count]×0.85) / floor(E[count]×1.15)
min/maxValue = ceil(targetValue×0.9) / floor(targetValue×1.1)
```

以下“价值”单位均为一阶折算值；实物数量只统计真实击杀时掉落的一枚枚妖丹。每层恰有 5 精英和 1 Boss。

第二层的声明数量下界为 51，但考虑阶位与价值下界后的可行物理下界为 52：五枚二阶、一枚三阶至多比同数量一阶多 7 点，51 枚无法达到 59 点。其余层的数量区间均全范围可行。所有层的价值上下界均可达。表格的上下界不是彼此自由组合的矩形，例如最高价值与最低数量不一定可以同时出现。

高阶价值采用线性 1…7，不使用旧精英/Boss 的 5…40 一次性阶位奖金。第九层实物比第一层少，但折算均值仍按旧目标增长。旧第六层击杀值 108 本来就高于第七层 105，保留这个顺序；加上既有清层奖励后，九层总值均值仍逐层上升。随机区间有重叠，不承诺每一局都单调增长。

## 有界采样与兜底

1. 输入严格检查 floor 1…9 与 seed 0…`0xffffffff`。`0` 是真实种子，不替换为默认值。
2. 用 `seed XOR imul(floor,0x9e3779b9) XOR 0x434f5245` 做域分离，再以两次奇数乘法和位混合雪崩，初始化本模块私有 Mulberry32。每次调用独立重建状态，不读取时间、`Math.random` 或战斗状态。
3. 每次候选按稳定编排顺序给所有实体做一次 Bernoulli 判断。只在整层**数量和价值均合格**时接受，最多 16 次。正常路径不会按价值择优或强制 Boss 掉落。
4. 16 次均失败时，以 `round(E[count])` 枚和精确 `targetValue` 构造可行阶位配方。对各阶可用数量做二进制分块，二维有界背包记录首次可达的 `(count,value)`，按前驱回溯。每层最多缓存一份 8 项配方。
5. 在各阶实体池中做局部 Fisher–Yates，按配方挑选互不重复的实体，最后按原编排顺序返回。因此每条记录仍来自真实实体、阶位正确、至多一枚，且没有额外补发实体。

当前九层的可行兜底见下表。它是预先排好“哪些真实击杀会掉落”的计划，不是退出时补足。

|---|---|---:|---:|

所有配方都可由当前编排提供、命中双预算。因为背包的 count 和 value 倒序更新，每个二进制块只用一次；回溯每步严格减少 count，最多 `round(E[count])` 步。采样上限 `16×682=10,912` 次随机判断，兜底选择最多 66 次随机判断，所以**任意 uint32 种子都在有限步骤内得到合法计划**，不依赖碰运气终止。测试将 `Math.imul` 临时故障注入为零，使每次候选全掉落、必定超预算，验证九层都耗尽 16 次后正常返回。未来改编排若使配方不可达，模块明确抛出内容错误；当前九层不存在该情况。

每层缓存最后一次 `{seed,plan}`，总计最多 9 份计划（按规则上限最多 533 项键值）；缓存淘汰不影响结果。背包只在首次需要该层兜底时创建，临时 `Int16Array` 最大 14,874 字节，回溯后仅保留 8 项配方。静态实体表共 4,770 项，不随 seed 数量增长。没有无界 seed 缓存。

兜底有意不承诺原角色概率：例如当前配方均不选 Boss。它只影响极小的采样耗尽尾部，因此总体不是数学上完全等同于无限重抽的条件分布。独立均匀随机模型下，九层单次合格率约 47.95%–63.53%，16 次耗尽率约 `9.79e−8`–`2.91e−5`；具体见报告。该概率是模型估计，不是对全部 2³² 个种子的枚举结果。

## 接入、版本与验证边界

父任务应使用已验证的原始 seed 重建一次整层计划，再对每次真实击杀读取：

```js
const drops = buildCoreDropPlan(floor, savedLootSeed)
const rank = drops[`${wave}:${localId}`]
if (rank !== undefined) earned.cores += CORE_RANK_VALUES[rank]
```

入账去重沿用父任务真实击杀台账。纯模块不读台账、不做存档迁移、不发清层/首通奖励，也不替父任务证明旧快照兼容。任意子集收益为该子集命中值之和，清空子集就是 0；不存在“先给最少枚数”“Boss 最后补足”或失败补发。

保存独立 loot 版本与初始 seed，恢复时不得传入已推进的战斗 RNG。测试固定了 `0xffffffff` seed 在全部九层的 v1 计划 SHA-256，防止后续实现调整悄悄重抽既有存档。变更算法、概率、阶位或编排时需要父任务显式处理版本兼容，不应只更新快照测试。

`tests/xianxia-tower-loot.test.mjs` 覆盖冻结结构、非法参数、零和最大 uint32、缓存淘汰后的重建、JSON 输入恢复、实际战斗状态不变、全部 180 波实体顺序与 `TowerRun._registerWave()` 对齐、4,096×9 个计划双预算和条件概率、任意击杀子集、恒零随机源兜底。它不替代父任务的击杀入账、暂停恢复、失败结算或旧档迁移集成测试。

## 纯接口与 UI 使用

均从 `js/xianxia/TowerGrowth.js` 导出：

| 接口 | 返回／用途 |
|---|---|
| `GROWTH_STAGES` | 按角色等级递增排列的九条递归冻结记录 |
| `growthStageAt(xp = 0)` | 通过原 `cultivationAt` 返回当前阶段记录；XP 非法沿用 `RangeError` |
| `skillStage(id)` | 返回对应学习阶段记录，未知 ID 返回 `null` |
| `GROWTH_SKILLS[].learnLevel` | 对应阶段 `minLevel`，由同一张表派生 |
| `GROWTH_EVOLUTIONS[].learnLevel` | 同上，分别 19／22／22／25 |
| `skillRequirement(state,id,options)` | 原报价结构不变；未达阶段新增 `reason: 'stage-locked'` |

每条阶段记录含：

```js
{
  id: 'zhuji-middle',
  realm: '筑基',
  phase: '中期',
  label: '筑基中期',
  minLevel: 13, maxLevel: 15, // 角色总等级
  minRank: 4, maxRank: 6,   // 当前大境界内的阶数
  skillIds: ['sj_mark', 'sj_bone']
}
```

阶段 ID 依次为 `lianqi-early/middle/peak`、`zhuji-early/middle/peak`、`jindan-early/middle/peak`。UI 可直接用 `skillStage(id).label/minLevel/skillIds` 分组和解释门槛；交互是否可执行仍以 Campaign 对 `skillRequirement` 的当前判断为准，不可仅看分组或 `rankCap`。

失败优先级保持“满级→教学→塔内场所”，再检查新阶段，然后检查原有境界升级上限、通层、前置、SP。因此 Lv1 请求金刚可能同时缺点且缺阶段，首先返回 `stage-locked`。UI 应将其显示为对应阶段要求；本次没有修改 UI 的错误文案映射。

## 旧档与快照兼容

Campaign 仍为 schema3，Run 仍为原 schema；没有新增任何保存字段。

- schema3 中先前合法的低阶段技能、点数及经卷逐字保留，继续进入 `combatLoadout` 并参与战斗。未达到新的学习阶段时，只拒绝继续加点。
- 特殊技能原读档校验只检查点数、等级上限、经卷与通层，不调用新学习门槛；维持这一关系。
- 进化原校验通过“上一等级的学习报价”验证持有等级。新增兼容选项 `skillRequirement(..., {ignoreStage:true})`，只跳过这次新增的阶段判断；原角色境界、通层、母／心等级、经卷归属及 SP 校验仍在。
- Campaign 只在**验证已持有进化**和**执行既有 schema1/2→3 分配迁移**两处使用 `ignoreStage:true`。正常 `_learn` 不传此参数，也不转发 action 中同名字段；测试验证不能通过 action 自带 `ignoreStage` 绕过新门槛。
- schema1/2 的既有兑换迁移仍可能因原 36 点预算等规则重新分配旧版逐级货币投资，这是先前规则；本次不会再因阶段后移额外删减。已迁移 schema3 无二次迁移或补偿。
- Run 验证不使用学习阶段，只保留原技能等级与进化母技能等战斗快照约束，故无需修改 Run。旧阶段进化继续替换母功法；其心法从 5 降到仍合格的 4 时，不会因为新阶段而误删该进化。

不能以 `ignoreStage` 代替用户新学习的授权判断，也不能放宽全局点数、经卷、进化前置或零级键校验来兼容旧档。
